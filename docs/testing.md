# Testing

Two runners, three layers:

- **`bun test`** — unit, integration, and component tests, colocated as `*.test.ts[x]` next to the code they cover (one exception: the service worker's tests live in `tests/sw.test.ts` — `public/` is deployed verbatim, so no test files belong there). The shared setup (`tests/setup.ts`, preloaded via `bunfig.toml`) registers happy-dom so React component tests run under the same runner; the game engine itself needs no DOM (see [architecture.md](architecture.md)). happy-dom provides no IndexedDB — suites that need one inject a `fake-indexeddb` `IDBFactory` (or a Map-backed `AsyncKv` fake) per test instead of registering a global, mirroring the injectable-`Storage` convention.
- **`bun run test:e2e`** — Playwright browser smoke tests in `e2e/*.e2e.ts` against the production build. The file suffix matters: `bun test` auto-collects `*.test.ts` AND `*.spec.ts`, so E2E files must use `.e2e.ts`.

## Running the E2E suite

```bash
bunx playwright install chromium   # once
bun run test:e2e                   # builds and starts the prod server itself
```

The suite runs **two workers with file-level parallelism** (`workers: 2`, `fullyParallel: false` — tests within a file stay serial) against the ONE shared Next server (`pglite://memory`) and ONE shared game server (`PERSISTENCE=memory`). A parallel-safety audit cleared every spec file for this; **new spec files must keep the invariants**: signup emails carry a file-distinct prefix plus a run tag (two files can start in the same millisecond), `/api/worlds` reads are account-scoped (never assume yours is the only world globally), and only online-world (room-consuming) specs count against the game server's `MAX_ROOMS` (raised to 8 in `playwright.config.ts` for headroom — two workers, two room-consuming files, and the 5-minute idle-room eviction window). Browser-context storage (localStorage/IndexedDB/service worker) is Playwright-isolated per test, so concurrent files can't see each other's saves.

The **two-browser specs** (`multiplayer.e2e.ts`, `nether-online.e2e.ts`) are the CI runner's heaviest load: two live software-GL render loops at once (no GPU on CI), and the client's pose stream, mining progress, and prediction reconciliation all ride the rAF loop — when rendering starves the CPU, everything those specs assert on crawls, which is exactly the flake shape that red-gated deploys for a day. Three defenses are load-bearing: the quarter-size `TWO_BROWSER_VIEWPORT` (`onlineHelpers.ts` — raster cost scales with pixels and these specs assert on engine state, never pixels), the no-throttling Chromium launch args in `playwright.config.ts` (a backgrounded witness page otherwise stops applying server ticks), and `trace: "off"` (continuous recording — including `retain-on-failure`, which records every test and discards on pass — starves this CPU-bound runner; with `retries: 0` there is no retry to trace on, and the auto error-context snapshot covers failures). Keep the viewport and no-throttling args when touching these specs, and never re-enable continuous tracing.

**Retries are off (`retries: 0`) — fail is fail, success is success.** A retry-only pass masks a flake as green, so the suite carries no retries (on CI either); every flake gets fixed at the root, the way this suite's history already does (the no-throttling args, the chained heavy projects, the `poseSettled` aim gate, and a real engine bug in `4b4d58d`). The residual two-browser flakes were closed this way rather than absorbed. The co-op friend-dig had two causes: mining is not a discrete command — it rides the 20 Hz `mineHeld` pose stream — so releasing the mouse on the local prediction could leave the server never seeing it (it now **holds** the dig until the host confirms); and both accounts spawn at the same deterministic center-land point, so the friend fell into the host's shaft over an aquifer and couldn't break a block straight down (it now walks to its own pristine solid column first — `walkToDiggableGround`). `nether-online.e2e.ts`'s `holdItem` re-dispatches the creative give across ~30 s, since `creativeGiveItem` has no optimistic path and its full round-trip echo out-lasted the old 10 s poll on a build-slammed runner. The two-browser movement/sync plumbing (`poseSettled`, `flyTo`/`walkTo`, `walkToDiggableGround`) lives in `onlineHelpers.ts`, shared by both specs; `poseSettled` makes a networked action wait for its aim to round-trip placer→server→witness before it fires. A genuine one-off runner hiccup is a **re-run**, not a retry.

E2E tests assert through `window.__monecraft` (the live engine/renderer/input handle — `net` is the session in online play; also handy in the browser console) instead of pixels; the one render check uses `renderer.renderedTriangles()`. The shared `gamePage` fixture seeds a default profile + world and enters it through the menu (reloads auto-resume the tab's world), then fails any test that logs a console error; `menu.e2e.ts` instead drives the menus from empty storage with the plain Playwright `test`. The fixture's `pauseOnBoot` option pauses the engine before its very first step (a setter trap on the `__monecraft` assignment) — required by any test that needs the world byte-identical to fresh generation, because worldgen leaves random-tickable blocks (growable kelp, cave-exposed dirt) near spawn and even the boot window can otherwise produce a `Math.random` block edit. `determinism.e2e.ts` opts in.

Playwright boots **two** servers (`playwright.config.ts`): the Next production build with a full online stack on an in-process ephemeral Postgres (`DATABASE_URL=pglite://memory` — no Docker; `db/index.ts` applies `db/ddl.ts` at boot) and the Bun game server (`PERSISTENCE=memory`) on port 18080. The offline suites never touch either backend; `multiplayer.e2e.ts` and `nether-online.e2e.ts` exercise both (their shared account/registration walk lives in `e2e/onlineHelpers.ts`).

Because e2e runs the production build, **every suite runs with the service worker registering** — the existing suites double as a non-interference regression (the fixture's console-error gate catches a worker that breaks a page), and each test's fresh browser context starts with empty caches, so nothing leaks between tests. Only `pwa.e2e.ts` goes offline.

**happy-dom has no 2D canvas context**: generated sprites degrade to a transparent data URL in component tests — assert sprite pixels in the pure `lib/ui` tests and component structure via roles/labels/`data-icon` attributes, not image sources.

**happy-dom has no `AudioContext`** (and the `zzfx` package instantiates one at import): everything above the `SynthBackend` seam is pure and tested with a recording fake (see `audioDirector.test.ts`); the WebAudio glue itself (`synth.ts`, `musicPlayer.ts`, `rainLoop.ts`) plus real synthesis quality belong to the manual gameplay pass.

**Known limitation:** headless Chromium cannot engage pointer lock (`requestPointerLock` never resolves). `acquirePointerLock` in `e2e/helpers.ts` tries the real thing, then falls back to forcing the input controller's lock flag — so key/mouse → engine wiring is still tested end to end, but real lock acquisition and look-around feel remain in the manual gameplay pass, along with visual quality. That manual pass is now only required for changes to pointer-lock handling, touch-control handling, or visual appearance.

**Touch: the real-device checklist.** The touch e2e drives real PointerEvents but not real fingers, and Playwright's `hasTouch` doesn't flip `(pointer: coarse)` — the `touchMode` fixture option forces the mode instead (detection is unit-tested). What only hardware can verify (run on an iPhone Safari landscape, an iPad, and an Android Chrome phone when touch behavior changes): auto-detection fires (and doesn't on desktop), first tap unlocks audio, three simultaneous contacts (walk + look + jump) with no stuck movement in any lift order, tap-vs-hold feel and `TOUCH_*` constants (config.ts / tuning.md "Touch feel"), no pinch/double-tap zoom or long-press callout, safe-area padding on notch phones, rotation mid-play, app-switch → paused and resumable, PWA install in landscape, and a framerate spot-check on a mid-tier phone.

## The worldgen hash policy

Saves store only the world seed plus block-change deltas, so `generateWorld` must produce byte-identical output for a given seed forever. The digests in `generation.test.ts` enforce that.

**If a hash test fails after your change, your change breaks every existing save. Fix the code, never the hash.**

Re-baselining the digests is legitimate in exactly one case: a **deliberate worldgen change** — flag it in the PR and CHANGELOG, and bump `WORLDGEN_VERSION` so affected worlds discard their stale block-diffs (rebooting from their seed) rather than corrupting.

To regenerate digests: temporarily log the computed hash in the failing test, run `bun test`, and paste the new values into `lib/world/generationBaselines.ts` in the same commit as the cause.

The digests are also an **engine-portability contract**: since worldgen v11, every seed-determined noise call uses the bit-portable implementations in `lib/world/noise.ts` (polynomial sine, integer hashes — only IEEE-exact operations), so the same seed generates identical bytes on every JS engine. `e2e/determinism.e2e.ts` proves it in CI by recomputing the full-size world digest inside Chromium/V8 (under the fixture's `pauseOnBoot`, so no simulation step can edit a block before the hash) and asserting it equals the Bun/JSC baseline in `lib/world/generationBaselines.ts` — this is what lets a browser client and a multiplayer Bun server share worlds by seed + block diff. `lib/world/noise.test.ts` additionally pins exact golden doubles of the noise primitives. New worldgen code must import its noise/trig from `lib/world/noise.ts`, never `Math.sin`/`Math.cos` (engine-defined per ECMA-262 — the reason the old digests were only valid on a pinned Bun).

The **worldgen batch (v11 → v12)** is the most recent legitimate re-baseline, and the first to re-roll BOTH dimensions' digests: deep **redstone ore** re-rolled all seven overworld digests (the pass runs last on its own PRNG and replaces stone only, so every structural probe — and even the in-region meshing position snapshot, since ore swaps one solid cube for another — passed unchanged), and **nether fortresses** re-rolled the four nether digests (placed after the lava flood and before the bedrock caps, again leaving every prior probe green; only the glowstone anchor probe learned that a fortress brick roof counts as a ceiling).

The **portable-noise worldgen (v10 → v11)** was the prior re-baseline: same wave formulas on `portableSin`/`portableCos`, plus an integer-hash `hash2D`. All seven digests re-rolled; **every structural probe passed unchanged** — the polynomial sine tracks the real one within ~6e-8, so terrain structure is preserved and only scattered single-block flips (cobble speckle, cave edges, flora patterns) moved the hashes. This bump also retired the old "case 2" (a Bun version bump could shift `Math.sin` results): the CI Bun pin is no longer load-bearing for worldgen, though it stays pinned for plain reproducibility.

The **deep-cave lava worldgen** was the prior re-baseline: the four worldgen digests and the in-region meshing snapshot were re-rolled and `SAVE_KEY` bumped v6 → v7. As with dungeons the structural probes (surface heights/biomes/snow/water) were left unchanged on purpose — `placeLava` runs after `placeOres` so it can't shift the ore→tree RNG stream, and the lava sits at or below `lavaLevel`, so the surface is byte-identical. A probe asserts lava is present and never rises above `lavaLevel`. Note the per-voxel **lighting** change re-rolled nothing: light is a derived runtime cache, never part of the generated bytes, and the meshing snapshot hashes only vertex positions — the new `aLight` attribute leaves them untouched.

The **0.7.0 dungeon worldgen** was an earlier re-baseline: the four worldgen digests and the in-region meshing snapshot were re-rolled and `SAVE_KEY` bumped v5 → v6. The structural probes were left unchanged — dungeons are wholly underground, so the surface bytes are identical.

## Writing new tests

- Pure logic (inventory, spawn rules, a new system): unit-test the module directly.
- Gameplay behavior: boot a small engine — `new GameEngine({ seed, rng, worldSize: { x: 64, y: 150, z: 64 } })` — and step it with synthetic `FrameInput`. Inject a seeded `rng` (see `mulberry32` in the engine tests) for determinism.
- The world boots at dawn with hostiles nearby; use the `calmDaytime` pattern from the engine tests when testing unrelated mechanics.
- A ray origin exactly on a voxel boundary no longer drifts onto an axis the ray doesn't travel (that DDA degeneracy — the reason a never-moved online joiner couldn't mine — is fixed and pinned in `queries.test.ts`). What remains is honest geometry: a ray that genuinely tilts toward a boundary it starts on enters the neighbor column immediately — so when a test means "this specific block", aim at the block's **center** from the actual position (the `forceDigStraightDown`/`topAims` pattern), never a fixed pitch.
